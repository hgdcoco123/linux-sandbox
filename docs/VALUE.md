# 价值证据：解释是否让"下一次尝试"更容易成功

## 一句话

在 3 个任务、3 种反馈条件、2 种 Agent 上：**没有解释时 0/3 修好；给结构化分析时 2/3 修好**，
两个 Agent（规则表与真实模型）结果一致。说明进步来自**分析里携带的事实**，不是模型更聪明。

## 方法（可复现）

`tools/agent_loop_demo.py`，process 模式，**不需要 sudo**。

每次尝试：写一个会失败的 shell 程序 → 沙箱执行 → 拿 report →（在 `analysis` 条件下）用
`sandbox_ai` 分析 → Agent 依据看到的反馈写下一次程序 → **验证器**（不是模型）判断是否达标。

关键设计——**信息不对称**：

| 谁知道需求 | 怎么知道 |
|---|---|
| 验证器 | 直接读 `specs/<task>.txt`（`expected=42`、`max_bytes=64` 等） |
| 被测程序 | **读不到**：spec 放在程序的 `cwd` 之外，挂载/路径都不通 |
| 分析层 | 能读到：spec 目录作为 `artifact_root` 进入证据，可被引用 |
| Agent | 只能看到该条件下给它的反馈文本 |

因此"目标"只能写成"让产物满足 spec 的要求"——不知道 42 还是 done。谁想修好，就必须从反馈里
把那个事实**取出来**。三种反馈：

| 条件 | Agent 看到什么 |
|---|---|
| `none` | 什么都不给，重复提交同一程序 |
| `report` | **完整 report JSON**（沙箱自带的一切：verdict、exit_code、errors、流统计…）。这是公平基线——任何用这个沙箱的人都有它 |
| `analysis` | `sandbox_ai` 的结构化输出（summary / facts / missing_info / next_steps 及其引用原文） |

任务：`write-from-spec`（期望 42）、`exit-clean-from-spec`（期望 done 且退出 0）、
`trim-to-limit`（期望 ok 且 ≤64 字节）。最多 3 次尝试。

## 结果（`qwen-plus`，2026-11-07，单机）

| Agent | 反馈 | 修好 | 平均尝试次数 |
|---|---|---|---|
| 规则表 | `none` | **0/3** | 3.00 |
| 规则表 | `report` | **0/3** | 3.00 |
| 规则表 | **`analysis`** | **3/3** | 2.00 |
| 真实模型 | `none` | **0/3** | 3.00 |
| 真实模型 | `report` | **0/3** | 3.00 |
| 真实模型 | **`analysis`** | **2/3** | 2.33 |

规模：18 条 loop、**49 次沙箱执行**、8 次分析（全部通过 schema 与引用校验）、约 40 次模型调用。

两条值得单独说的证据：

1. **规则表 3/3**：它只会对反馈文本做正则（`expected=(\w+)`、`max_bytes=(\d+)`）。
   它能修好，说明分析**真的把 spec 里的事实带出来了**，而不是"模型自己猜中了"。
2. **同一份 report 不够（0/3）**：report 里有 verdict、exit code、流统计，但没有"期望值是多少"。
   这正好划出界线——**沙箱负责"发生了什么"，分析层负责"这意味着什么、缺什么"**。

## 修好 3/3 之前，先修了 harness 自己

第一次跑出来是 2/3，两个失败都不是"解释无用"，而是测量脚本的错：

1. 三个任务的 `spec.txt` 放在同一目录 → 一个任务的证据里混进别的任务的期望值，分析照着
   `write-from-spec.txt` 的 `expected=42` 去修 `trim-to-limit`。改成每任务一个目录。
2. 所有任务共用 `loop` 作用域 → 别的任务的 `echo 41` 以 `origin=history` 的身份出现，分析据此
   编出"spec 要求 41"。改成每任务一个 scope。

修完规则表 2/3 → **3/3**；模型仍是 2/3。这两条正好说明"测量脚本的错误会伪装成被测对象的错误"。

## 模型仍差的那一个：分析把 `max_bytes=64` 读成"恰好 64 字节"

`trim-to-limit` 的 spec 是 `expected=ok` + `max_bytes=64`（内容必须是 `ok`，且不超过 64 字节）。
模型第二次尝试写了 64 个 `x`：它满足了大小，丢掉了内容。原因在分析文本——那一次的分析写的是
"spec.txt 明确要求 answer.txt 大小为 64 字节"，把上界读成了精确值，并把 `expected=ok` 漏掉；
模型忠实地执行了这条错误的分析。

规则表反而 3/3，因为它的正则取的是 `expected=ok` 直接写出。**这是"解释错得比没有解释更糟"的一个实例**，
也是这条链路上最值得记录的失败：拼的不是提示词，是"分析文本本身可能引入错误"。

## 另一个没修好的任务（历史记录）

`trim-to-limit` 两种 Agent 都是 0/3。原因不是模型笨：那一次分析**没有引用到 `specs/trim-to-limit.txt`**
（检索没把那一行带进上下文），于是反馈里没有 `expected=ok / max_bytes=64`，Agent 无从下手；
真实模型只能猜，写出了 `/bin/sh` 不支持的语法后连续失败。

这是**检索覆盖**的问题，不是"解释无用"。后续若要提高，应该改检索（小文件提权 / 强制带上 spec），
而不是让模型多试几次。

## 边界（不要过度解读）

- 3 个任务、18 条 loop、单一模型、单机；成功率是**样本内**数字，不是基准。
- 任务是"从证据里取出一个事实"，属于分析层最擅长的形态；真实的代码修复要难得多。
- `process` 模式没有隔离，也没有产物导出语义；这里测的是"信息是否够用"，不是隔离。
- 0/3 的基线不代表"没有解释就绝对不行"——强的模型可能猜中；本组里的 `qwen-plus` 没猜中。

## 怎么自己复现

```bash
cmake --build build --parallel
export SANDBOX_AI_BASE_URL=... SANDBOX_AI_MODEL=qwen-plus SANDBOX_AI_API_KEY=...
python3 tools/agent_loop_demo.py --sandbox build/sandbox --work /tmp/loop --provider compatible
```

不带 `--provider compatible`（即 `demo`）时不需要任何凭据，用离线提供者跑通整条链路——
但那种情况下"分析"是模板文本，`analysis` 条件不会带来提升，这本身也是一条对照。
