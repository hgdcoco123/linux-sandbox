## 0.5 补充与覆盖说明

- 新增批次内 FIFO 并发/内存/pids 预算，不是主机全局调度器；最多 256 任务、32 并发，不支持批次崩溃后自动接管/续跑。
- stdout/stderr 写盘已移至有界工作线程；下文关于“输出写盘同步”的描述是前版历史。状态保存、日志、文件传输仍可能同步阻塞。
- 输出队列每流 256KiB，满时背压。普通文件 I/O 可无限期卡在内核，线程 join 不承诺硬关闭期限。
- isolated 任务受各自 cgroup 限制；批次预算只预留目标配置上限，不包含宿主监督器/线程栈等总成本。process 模式依然无隔离。
- 任务执行记录保留于 /tmp/sbx-tasks-XXXXXX，具体路径写入批次记录；没有自动空间治理。删除前需确认相关监督进程和任务已结束。
- 0.4 的 Linux 使用路径已有用户提供的成功记录；0.5 新增多线程和调度必须重新验收。未运行 ThreadSanitizer 或长期压力测试。


0.4 核心整理见 CORE_STRUCTURE.md。0.3/0.4 的真实运行验收记录见 VALIDATION.md；当前状态见上方"验证状态"。

runtime 和映射源的路径组件不得含符号链接。对象替换或路径失效时拒绝准备。
`workspace.input = "snapshot_copy"` 时复制在 launcher 启动前完成并原子发布（`renameat2` NOREPLACE），

## 0.3 扩展补充

- 已增加连续会话、流式输入/偏移输出、目录快照和产物导出，0.3 已通过用户提供的真实 Linux 集成验收；0.4 重构后的重测并入 0.6 的全量隔离验收（见上方"验证状态"）。
- isolated 会话中受管理 `/output` 允许执行编译产物；原单次映射仍禁止执行。
- 文件复制只接受目录和非硬链接普通文件，拒绝符号链接及特殊文件；不能当作原子文件系统快照。
- 单次复制上限 4096 条目、256MiB，目录深度最多 64；它不是执行期间的磁盘配额。
- 文件传输与输出写盘为同步 I/O，慢存储会影响事件循环和期限响应。
- 每个会话只执行一条活动命令，最多 1024 条；无持久 Shell、PTY 或保留后台服务。
- 关闭/中断后保留记录和工作区，失败复制可能保留 `.sbx-copy-*`，尚无自动空间治理。
- v2 execute 按会话内 request_id 持久化去重；v1 无 ID 请求仍无去重保证。结果 uncertain/interrupted 时不得换 ID 盲目重跑；没有外部副作用 exactly-once 保证。
- cleanup 是保守回收，不是任务接管；process 模式缺少归属证据时仍 unresolved。

以下为原单次执行边界；其中“未实现产物交付”部分已由上面的受限目录交付补充。

1. 共享宿主内核，不抵御内核漏洞；baseline 是兼容型拒绝策略，不是完备的恶意代码 allowlist。
2. 重构后的隔离验收见上方"验证状态"；这条边界仍然成立：交叉编译成功不证明行为正确。
3. 支持可信本地配置提交者，不构成多租户权限平台。SDK 的上层必须限制路径、运行时和策略。
4. 只有一个 UID/GID 映射，附加组不承诺被清空。无特权 setgroups 被 deny 后不能假装调用清空成功。宿主来源权限和运行时兼容需要测试。
5. user namespace 和 cgroup 委派受发行版配置、AppArmor、systemd 和安装权限影响，不提供自动提权或静默降级。
6. runtime 来源不应包含嵌套挂载、socket、凭据或恶意并发修改；原型没有对所有来源目录进行递归安全审计。
7. 只有 /input、/output 目录映射；`snapshot_copy` 模式下输入是启动前复制好的副本，`bind_readonly`（默认）下仍是绑定，宿主并发修改可见。
8. 输出目录可产生任意文件/符号链接，软件不自动跟随、执行或信任它们；失败输出可能不完整。
   导出**整棵** `/output`，因此只要树里有一个符号链接/硬链接/特殊文件，整次导出都会被拒绝；
   单次执行此时报告"产物未交付"（`workspace.export.ok=false`、`verdict=harness_error`），
   而不是只丢掉那个条目。
9. 没有 I/O 带宽与 GPU 控制。磁盘方面：`/work`、`/tmp` 是 `size=limits.tmp_bytes` 的 tmpfs；**隔离模式下 `/output` 也是 tmpfs**，由 `size=workspace.max_bytes` 与 `nr_inodes=workspace.max_entries` 强制。会话里配额是**整个会话累计**（不存在按命令重置）；单次执行与批量任务各自是一条独立的磁盘边界，运行结束时一次性导出，因此没有"按命令重置"的问题。`mounts[target=/output].source` 是**最后一次导出落地**的宿主目录，不再是被挂进沙箱的工作区：运行期间该目录看不到新产物，导出失败时它保持原样。process 模式的 `/output` 仍是宿主目录绑定，没有运行期配额（诊断后端，不承诺隔离）。导出到宿主副本需要沙箱主动移交，失败会在结果里单独报告（`workspace.export`）。
10. **导出超时只表示监督端不再等待**：沙箱内的复制可能仍在进行，此时传输通道在**本会话内作废**
    （后续传输快速失败，直到会话关闭）。迟到回执按序号丢弃，不会被当成新请求的答复；它到达时
    主循环会把它记成 `stale transfer reply discarded`，**不会**因此判定会话出错。宿主传输目录以
    **fd** 传入沙箱，**不存在任何可见路径**，目标无法触达。
11. stdout/stderr 不保证全局顺序；exec 错误通道 EOF 仍有启动前异常死亡的观测歧义。
12. cgroup OOM 可能杀死 init，目标退出码可能未知；报告保留组事件，不伪造值。**OOM group kill 杀掉 init 时，`/output` 的 tmpfs 随 namespace 一起消失**：单次执行的产物无法交付，报告会明确写 `workspace.export.ok=false` 并把原因放进 `errors`（`summary` 仍是 `oom`），不会因为目标"没有非零退出"就报成功。
13. 控制进程被 SIGKILL/宿主掉电时不保证即时清理；恢复只能处理归属明确的资源。
14. cleanup 当前保留运行目录与报告，并不实现历史报告保留/过期删除策略。部分临时目录可能需要人工处理。
15. process 模式无隔离；主动逃逸、无限进程创建和不可中断睡眠不保证收尾成功。
16. 没有 PTY、GUI、远程服务、动态插件热卸载、稳定 C++ ABI 或镜像管理。

这些边界不是让必要限制可选：在 isolated 模式，任何已要求的机制设置失败都必须停止，不会自动改用 process 模式。
